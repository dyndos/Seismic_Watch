## 1. Итог выполнения

Журнал, предоставленный пользователем, содержит явные завершающие маркеры:

- `STEP #1 completed.`
- блок вычислений STEP #2 завершен переходом программы к STEP #3; **отдельной строки `STEP #2 completed.` в журнале нет**;
- `STEP #3 completed.`
- `STEP #4 completed.`
- `STEP #5 completed.`
- `PROGRAM GEAR1_for_CSEP: Job completed.`

В STEP #2 программа завершила подготовку GSRM/GCMT/PB2002, расчет всех 31 порогов и перешла к STEP #3. Поэтому по последовательности лога весь вычислительный конвейер выполнен. **Оригинальный исполняемый файл GEAR1 завершил расчет и прошел этап записи CSEP XML согласно журналу.** Сам XML впоследствии был предоставлен в виде локального файла и прошел отдельную потоковую проверку; результаты см. в разделе 6. Маркер завершения программы сам по себе не заменяет проверку артефакта.

В журнале также записано: `Random numbers generated with brng = VSL_BRNG_MCG31 = 1048576, seed = 1`. Это указывает, что запуск выполнен через авторский интерфейс VSL, а не через диагностическую замену RNG в GNU Fortran shim.

## 4. Важное наблюдение по GSRM и геометрии

В этапе 2 программа выполняла распространение номеров тектонических зон на соседние активные ячейки. После 109 итераций остались 101 orphan cell; исходный код вывел сообщение:

`Now giving up and zeroing strain rates in 101 orphan cells.`

Максимальная обнуленная скорость деформации — 9,13 × 10⁻¹⁷/с, или 2,9 nanostrain/year. Это штатное завершение оригинального алгоритма, но научное ограничение, которое нужно сохранить при оценке покрытия и неопределенности. Мы не переопределяем это поведение при аудите и не считаем отсутствие значения измеренным нулем в новых физических модулях.

Калибровочный GCMT каталог: 6 476 событий за 1977-01-01 — 2013-12-29, длительность 37 лет. Лог содержит распределение событий по четырем зонам границ плит и внутриплитной области, а также scaling factors для зон.

## 5. Опубликованный reference output и проверка XML

Официальная страница Dryad для архива Bird указывает, что в папке GEAR1 находится `GEAR1/GL_HAZTBLT_M5_B2_2013.zip` — сжатая версия CSEP XML-прогноза, ранее представленного в CSEP. Это опубликованный reference output, а не входная S-parent сетка `GL_HAZTBLT_M5_B2_2013.TMP`. Его можно использовать как независимый опубликованный ориентир для сравнения с пользовательским повторным запуском. См. [перечень файлов Dryad](https://datadryad.org/dataset/doi:10.5061/dryad.cnp5hqcjb).


Из журнала видно, что программа начала `Writing .xml file...`, завершила STEP #5 и напечатала `Job completed.`. Сам XML проверен отдельно по локальному файлу пользователя; подробности и ограничения проверки приведены ниже.

Для проверки самого `GEAR1.global.forecast.xml` добавлен потоковый валидатор [`research/validate_gear1_xml.py`](../research/validate_gear1_xml.py). Он рассчитан на крупный файл: читает XML по ячейкам, удаляет обработанные элементы из дерева, проверяет 6 480 000 ячеек и 31 значение в каждой, порядок координат, отсутствие отрицательных/NaN rates и контрольные интегралы по всем кумулятивным магнитудным порогам. Контрольная сумма SHA-256 считается во время разбора.

Команда запуска из корня репозитория:

```bash
python research/validate_gear1_xml.py "data/external/gear1/run/GEAR1.global.forecast.xml" \
  --output "data/external/gear1/xml_validation.json"
```

Первоначальный отчет валидатора был дополнен исправлением обработки `cellDimension` и текстовых значений внутри `<cell>`. Полученный отчет повторной проверки зафиксирован в приложенном `gear1_xml_validation_v2.json`.

Машиночитаемые данные полного журнала: `research/results/gear1_original_run_2014-2015.json`.

Значения магнитудных бинов записаны непосредственно текстом внутри элемента `<cell>`, а не отдельными дочерними элементами `<bin>`; валидатор поддерживает оба варианта. **Важное различие:** эти величины — математические ожидания/интенсивности числа событий, а не вероятности землетрясения в отдельной ячейке. Для получения вероятности хотя бы одного события нужна отдельная вероятностная модель (например, пуассоновское преобразование при соответствующем предположении).

## 7. Ограничение по времени выпуска прогноза

В метаданных XML указано:

- `forecastStartDate = 2014-01-01T00:00:00Z`;
- `forecastEndDate = 2015-01-01T00:00:00Z`;
- `issueDate = 2014-06-04T23:59:59Z`.

При этом журнал указывает последнюю дату события в калибровочном каталоге — 2013-12-29. Следовательно, по дате каталога явного использования событий 2014 года в калибровке не видно, но XML был выпущен примерно через 155 дней после начала заявленного прогнозного интервала. Поэтому **это не следует называть операционным прогнозом, опубликованным до 1 января 2014 года**. Для строгой проверки необходимо разделять два вопроса:

1. *Hindcast с отсечкой каталога на 2013-12-29*: можно сопоставить распределение GEAR1 с событиями всего 2014 года, отдельно подтвердив историческую доступность всех входных слоев.
2. *Проспективная оценка после фактического issueDate*: оценивать события только после 2014-06-04T23:59:59Z, с корректным усечением прогноза и наблюдений до конца периода.

Также текущая проверка является полной потоковой структурно-численной проверкой по нашим правилам, но **не сертификацией соответствия XML официальной XSD-схеме CSEP**. Она проверяет структуру, глобальную сетку, значения, диапазоны и согласование интегралов с журналом. Проверка XSD и проверка прогностической точности — отдельные этапы.
